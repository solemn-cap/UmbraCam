# Architectural decision log

## ADR023 — Fresh-grant-only screen sessions and staged implementation (2026-11-01)

The user requested Phase5 while Phase4 physical acceptance remains deferred. Establish screen-only consent/session and bounded geometry policy first. Preserve camera facades and their original two-argument interruption behavior; a separate overload lets screen interruptions prohibit same-grant recovery. Opaque object identity fences callbacks but is never treated as actual platform permission. Require fresh system consent in the future Android owner; do not persist/replay it or revive a stopped projection. Static screen content needs a different loss policy from camera progress. Claim publication once so late encoder errors cannot steal storage ownership. The proposed initial adapter is whole-display, silent, fixed-size surface-input MediaCodec/MP4 with explicit stop on geometry changes. No new module/dependency or actual Android recording is part of this first policy checkpoint. See [design](PHASE_5_DESIGN.md) and [verification](PHASE_5_POLICY_REPORT.md).

## ADR 001 — Two modules initially (2026-10-30)
Decision: app plus pure Kotlin core:recording. Reason: enforce platform-independent contracts without empty modules. Alternatives: monolith or immediate full module tree. Consequences: future feature extraction is deliberate, with some package movement later.

## ADR 002 — Native shell and navigation (2026-10-30)
Decision: Compose, Material 3, Navigation Compose; system appearance and saved back stack. Reason: official native lifecycle integration, accessibility primitives and configuration survival. Alternatives: manual route strings in rememberSaveable, Navigation 3, Fragment UI. Consequences: modest Navigation dependency; no ViewModel/Hilt until state/object graphs justify them. No persistent appearance preference yet.

## ADR 003 — Pinned build baseline (2026-10-30)
Decision: AGP 8.13.2, Gradle 8.13, JDK 17, Kotlin/Compose compiler 2.2.21, stable Compose BOM 2025.10.01, compile/target 36 and min 29. Reason: a conservative compatible stable toolchain rather than integrating newest releases without validation; API 36 meets the checked Play target requirement. Alternatives: AGP 9 migration, newer BOM, lower target/min API. Consequences: versions are stable pins, not claims of latest versions. No SDK was initially installed; SDK selection remains subject to build/device validation and release-time policy checks. AGP 8.13 supports up to 36.1. See [official compatibility table](https://developer.android.com/build/releases/agp-8-13-0-release-notes) and [Play requirements](https://developer.android.com/google/play/requirements/target-sdk).

## ADR 004 — Contracts before engine (2026-10-30)
Decision: states, source/error/session models and StateFlow engine interface only; no engine implementation. Reason: Phase 0 forbids recording implementation. Alternatives: eager MediaCodec pipeline, full reducer now. Consequences: constructor invariants are testable; actual serialized transitions and callback semantics remain future work. Interfaces may evolve based on hardware results.

## ADR 005 — No startup permissions or vault claims (2026-10-30)
Decision: declare no permissions/services in the source manifest; explicitly label unfinished screens and disable backup. Reason: shell needs no protected capabilities; future recordings are sensitive. Alternatives: predeclared permissions and realistic fake record controls. Consequences: future milestones must introduce appropriate grants/services and design encrypted storage; a placeholder does not protect files. AndroidX adds an internal signature-only receiver permission during manifest merging; no runtime/media grant or prompt is introduced.

## ADR 006 — Defer DI and persistence (2026-10-30)
Decision: no Hilt, Room, DataStore, CameraX or security libraries yet. Reason: no implemented feature uses them. Alternatives: scaffold all recommended technologies. Consequences: add each at its owning milestone with justification and meaningful tests.

## ADR 007 — Explicit modern backup exclusions (2026-10-30)
Decision: set allowBackup=false and fullBackupContent=false for older Android and exclude every supported app-data domain from Android 12+ cloud backup and Android device transfer using dataExtractionRules. Reason: lint identified that allowBackup alone is insufficient modern configuration, and future recordings are sensitive. Alternatives: rely on allowBackup only or selectively back up settings. Consequences: future persistence work must deliberately revisit backup/transfer policy and validate OS/OEM behavior; no backup guarantee is inferred from XML. See [Android backup configuration](https://developer.android.com/identity/data/autobackup).

## ADR 008 — Approved foreground single-camera implementation (2026-10-30)
Decision: user approved Phase 1; use CameraX 1.5.3 core/camera2/lifecycle/video/view, keeping the verified Phase 0 Gradle/Kotlin/Compose baseline. Add Lifecycle runtime-compose/viewmodel-compose 2.9.4 for observable business state and activity-retained ownership. Reason: official stable APIs provide preview, capability checks and muxed camera/audio output without a speculative custom encoder. Alternatives: latest CameraX 1.6.2, manual Camera2/MediaCodec or an immediate generic pipeline. Consequences: 1.5.3 is a deliberate stable pin, not latest; camera compatibility and physical output must be tested. New code stays in app/camera until extraction has value. See [CameraX release notes](https://developer.android.com/jetpack/androidx/releases/camera) and [video architecture](https://developer.android.com/media/camera/camerax/video-capture).

## ADR 009 — Stop on pause/rotation, explicit Start after return (2026-10-30)
Decision: an activity-scoped CameraStudioViewModel retains options/finalization state, but capture stops on ON_PAUSE/navigation/rotation. No foreground service, persistent recording or automatic recovery. Main-thread session coordination rejects stale callback IDs and lets Stop win over delayed Start. Reason: the approved single-camera milestone precedes background lifecycle implementation. Alternatives: lock orientation, continue recording in a service, or automatically restart after configuration change. Consequences: rotation can split a user's intended session; UI states this clearly, and a new user Start is required. Private coroutine scope finishes accepted finalization after ViewModel clearance and then cancels; it cannot survive OS process termination. Required camera/microphone source loss stops rather than silently falling back to a different input.

## ADR 010 — Staged private output and structural validation (2026-10-30)
Decision: record into noBackupFilesDir/camera/pending, check a 32 MiB free-space floor, structurally inspect finalized MP4 metadata, then ATOMIC_MOVE into recordings. Failed/unverified files go to quarantine or remain pending if storage prevents moving them. Reason: completed storage must never expose partially written output; keep earlier completed files intact. Alternatives: directly expose recording files, public MediaStore output or delete every errored output. Consequences: files are private, not encrypted, and no playback/export/Vault UI exists yet; uninstall deletes them. Metadata readability is not decoder/playback certification. A source-inactive or storage-full result may be preserved only if structural validation passes and the saved session retains a warning. Pending/quarantine accumulation and process-death reconciliation remain later work. Official [Finalize semantics](https://developer.android.com/reference/androidx/camera/video/VideoRecordEvent.Finalize).

## ADR 011 — Authorized service continuation and explicit recovery (2026-10-30)
User approved Phase 2. Supersede ADR 009 with an application-scoped controller and private typed, non-sticky foreground service. Accepted capture can continue when UI leaves; notifications are mandatory product controls. Starts require visible user action and permissions. Explicit same-lens/microphone Resume rotates the attempt token and retains earlier segments. Process death, force-stop and reboot never authorize automatic capture. No new dependency is needed.

## ADR 012 — Atomic journals and conservative crash reconciliation (2026-10-30)
Persist bounded private metadata through synced atomic properties files on one IO executor. Reconcile on explicit app launch, validate completed references and quarantine abandoned pending output. Corrupt metadata never deletes media. Successful publication with failed journaling retains the file and reports a warning. Room/DataStore await catalog requirements.

## ADR 013 — Finalization and foreground-promotion races (2026-10-30)
Finalize receipt fences publication; the missing-callback watchdog cannot release busy ownership during publication. Attempt-specific output and service teardown reject stale work. A real Samsung test caught immediate Start/Stop missing Android's foreground-promotion deadline. Promote pending ownership in onCreate, including canceled starts, then stop without acquiring Recorder. Latest revalidation is in PHASE_2_REPORT.md.


## ADR 014 — Recovery acquisition waits for usable output (2026-10-30)
Physical UID-level camera interruption testing exposed a recovery race. Repeated forced rebinds during finalization/service teardown queued camera close/open transitions around a newly accepted Recorder. Keep an existing binding after finalization, coalesce loading binds and avoid Retry rebinding a ready camera. Start/Resume cannot run while binding is loading. Preparing/Recovering may wait through non-error camera transitions within the existing ten-second deadline; explicit errors and required-source loss during Recording still stop immediately. Recording requires confirmed Start, available required sources and positive encoded bytes. Canceling a bind resets loading. This fixes the race without automatically restarting capture or weakening active-source gating.

The AppOps test changes UID mode, not package mode, asserts that denial took effect and restores the exact prior mode in finally. Physical execution is explicitly opt-in. See PHASE_2_REPORT.md for actual pass/failure evidence.

## ADR 015 — Advertised concurrency is not recording validation (2026-10-31)
Use CameraManager.concurrentCameraIds (API 30+) without adding dependencies or opening cameras. Preserve complete groups; missing or inconsistent metadata yields an actionable retry, not an unsupported verdict. API 29 explicitly reports that the standard query is unavailable. Concrete dual stream/quality validation and compositing belong to Phase 4.

## ADR 016 — SOS naming and supplied launcher identity (2026-10-31)
The user requested SOS Mode in place of Safety Mode and supplied UmbraCam Icon.png. Preserve the saved safety route. SOS remains an honest preview without emergency-response claims. Package the supplied artwork in an adaptive icon with black padding that preserves its rectangular proportions. Keep the monochrome recording notification icon.

Phase 3 platform references: [CameraManager concurrent inventory](https://developer.android.com/reference/android/hardware/camera2/CameraManager#getConcurrentCameraIds()) and [adaptive launcher icon geometry](https://developer.android.com/develop/ui/compose/system/icon_design_adaptive).

## ADR 017 — Phase 4 composition feasibility gate (2026-10-31)

Use existing CameraX 1.5.3 shared Preview/VideoCapture composition as the first candidate for front/rear PiP and split output. No dependency upgrade or custom encoder is justified yet. A bounded spike must prove both input progress signals, composed output and lifecycle behavior. CameraState.OPEN and composite bytes do not establish that both cameras remain live. If independent health cannot be established, dual Start stays unavailable while an alternative is designed. Preserve single-camera guards, explicit recovery and finalized segments. See [PHASE_4_DESIGN.md](PHASE_4_DESIGN.md). This records a design, not completed capture functionality.

## ADR 018 — Dual binding identity and source-loss evidence (2026-10-31)

Phase4.1 confirmed both per-device interop callbacks through pinned composition on one API30 emulator. Carry lens-facing constraints alongside exact-ID filters; null facings entered the same-camera path. Treat the single public composition wrapper separately from the two required source identities. A changed immutable layout requires a fresh binding lifecycle identity; reusing the earlier owner retained PiP after unbindAll in the experiment. Preserve an independent source-loss warning even when Recorder finalizes with error0. Distinct-moving-input provenance remains open because file-backed inputs advertised no concurrent pair. Keep product dual recording unavailable until its gates are satisfied. See [feasibility report](PHASE_4_FEASIBILITY.md).

## ADR 019 — Isolated dual source policy with preserved single-camera boundary (2026-10-31)

Reuse the existing transition machinery internally while retaining SingleCameraSessionCoordinator and its one-camera validation. Dual sessions require exact front/rear identities, fresh advancing progress for both, Recorder Start, encoded bytes and selected microphone readiness. Use opaque acquisition tokens with generations and an injected monotonic clock; expiry is checked before new evidence and requires owner-scheduled tick. Preserve source-loss warnings independently of Recorder success. Claim publication only once; late backend errors cannot release a storage-owned attempt, while explicit publication failure can finish honestly. Final-frame geometry is a pure contract; platform inverse transforms await runtime validation. No Android/UI integration or dependencies are added by this decision. See [domain report](PHASE_4_DOMAIN_REPORT.md).

## ADR020 — Causal input modulation establishes emulator provenance (2026-10-31)

Use independent exposure markers through existing CameraX camera controls to establish each input’s saved-video contribution when replacement feeds remove concurrent metadata. Require exact advertised pair, per-device manual-sensor results, decoded-region darkening/recovery, and an unaffected visible other region. Repeat both layouts and primary orders. Resolve the secondary control with an unserved preliminary Preview, fully unbind, then apply only while the camera is active in the composed pair; this pinned-backend technique is test-only. No extra active stream, callback-submitted request or eligibility bypass is allowed. Four cases passed, closing the bounded emulator provenance gate; app integration and physical acceptance remain required. See [provenance report](PHASE_4_PROVENANCE_REPORT.md).

## ADR021 — One service owner and compatible dual journals (2026-11-01)

Route single and dual through one stable controller session flow and existing typed non-sticky service, keeping the single-camera boundary. Use a fresh dual binding identity for accepted acquisition, captured core tokens, read-only per-device callbacks, delayed-receipt rejection and owner-scheduled health ticks. Reject missing requested permission before service start. Freeze settings while busy, validate recorded geometry before publication and retain source/storage diagnostics independently. Preserve the v1 writer signature/format; v2 carries explicit dual settings and bounded diagnostics. Reconciliation restores only a terminal warning and media references, never selection or authorization. Initial geometry is portrait/rotation0. Emulator integration and forced-termination results are in [the integration report](PHASE_4_INTEGRATION_REPORT.md); controls and physical acceptance remain separate tasks.

## ADR022 — Explicit native dual controls (2026-11-01)

Extend the approved Material 3 Camera Studio. Query public capability metadata only when Studio is shown or explicitly refreshed. Present exact advertised two-camera front/rear groups as choices, never inferred subsets. Default to Single; Dual defaults to rear-main/front-inset portrait HD, with an explicit split alternative and microphone opt-in. Keep the selected layout/audio on repeated mode taps. Recheck inventory at Start eligibility and revalidate independently in the capture adapter. Keep Dual selected on bind failure so the user sees the problem and deliberately chooses retry or Single. Refreshing metadata never starts capture. Freeze controls during binding/capture; requested microphone loss must not silently become a silent dual session. Physical acceptance is a separate milestone.

## ADR023 — Deliver a bounded useful beta before advanced features (2026-11-01)

The user authorized combining native silent screen capture and a completed-recordings library in the next pass. Reuse platform MediaProjection/MediaCodec/MediaMuxer and existing file publication without dependencies. Require fresh system consent, typed foreground ownership and real sample readiness. Stop on display change instead of introducing unvalidated resize transforms. Keep screen and camera storage namespaces separate and acquisition mutually exclusive. Export through user-selected Create Document; require confirmation for deletion and remove deleted session references. Rename the Vault preview to Recordings because this milestone provides no encryption. Preserve the approved Material3 identity and icon. SOS, encryption, overlays and internal audio remain deferred. Emulator evidence does not qualify physical devices or a store release.
## ADR024 — Advertise capture paths only when the adapter implements them (2026-11-02)

Separate hardware presence from capture support. ReactionCapability reports supported composition layouts and audio-track adapters independently from camera/microphone hardware. Request validation requires both hardware/source availability and the concrete adapter path. Pass one immutable ReactionRecordingRequest from UI through consent and revalidate it after chooser return and before foreground acquisition. Keep this request policy ephemeral; never journal permissions, chooser data or projection authorization. At this checkpoint the Android adapter was screen-only; ADR025 records its subsequent combined-camera implementation. See [Milestone 5 progress](MILESTONE_5_PROGRESS.md).

## ADR025 — Compose screen and front camera into one silent output (2026-11-02)

Implement combined Reaction Studio output with platform Camera2 + MediaProjection external textures and GLES into the existing AVC encoder surface. Support PiP and split, use CAMERA permission only at Start and point-of-open, and include camera in the media-source readiness gate before RECORDING. Use the typed camera foreground-service ownership only for combined sessions. Camera loss interrupts and finalizes valid partial output; the source requirements are journaled without any consent or authorization. No new dependency is required. Emulator results are bounded to the tested API29/API36 AVDs; API30, physical compatibility, sustained performance and all audio capture remain unverified/unavailable.
